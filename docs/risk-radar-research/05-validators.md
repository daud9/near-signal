# Validator concentration and performance risk

## Verified protocol and RPC facts

NEAR defines an epoch as consecutive blocks with a fixed validator set; validator rotation occurs at epoch boundaries. The nearcore architecture note says the mainnet epoch length is 43,200 blocks (about 15 hours), and validator selection for T+2 is based on high-stake accounts at the end of epoch T. [1] The official RPC reference lists `status`, `block`, `validators`, and `EXPERIMENTAL_validators_ordered` as network methods and says requests are JSON-RPC POSTs to the provider root. [2]

The live mainnet RPC was queried on 2026-11-14 using `POST https://rpc.mainnet.near.org/` with `{"method":"validators","params":{"epoch_id":"HrjtXTcwMkpGwgbQqNJih2BMPbNmaTeuSTpCbHzPFwvd"}}`. The response contained `epoch_height`, `epoch_start_height`, `current_validators`, `next_validators`, `current_proposals`, `prev_epoch_kickout`, and `validator_reward_paid_prev_epoch`. Each current validator record returned `account_id`, `public_key`, `stake`, `is_slashed`, `num_expected_blocks`, `num_produced_blocks`, `num_expected_chunks`, `num_produced_chunks`, `num_expected_endorsements`, `num_produced_endorsements`, per-shard variants, `shards`, and `shards_endorsed`. This field observation is from the live response, not a search snippet.

The same live snapshot had epoch 4970, start height 224,524,337, and 355 current validators. Stake concentration computed from `current_validators[].stake` was: top 1 = 5.665%, top 3 = 14.459%, top 10 = 35.905%, top 20 = 57.640%; stake HHI = 0.02163. The largest account was `astro-stakers.poolv1.near` at 5.665%. These are snapshot observations, not a historical trend.

For performance, the snapshot totals were 3 block misses, 231 chunk misses, and 911,333 endorsement misses across current validators. Minimum individual rates were 99.497% for blocks, 97.893% for chunks, and 0% for endorsements. The endorsement minimum must not be treated as a network outage: it is a validator-level production field and can reflect role/assignment or a validator that produced none of its expected endorsements. Inspect the per-validator expected/produced values and `prev_epoch_kickout.reason` before escalating.

The prior-epoch kickout list had 11 observed accounts. The returned reasons were `NotEnoughChunkEndorsements`, with `expected: 43198` and `produced: 0` for most listed accounts, and `produced: 18623` for `staker-rene.pool.near`; `is_slashed` was false for all current validators in this snapshot. This is an observed validator-performance result, not a claim that the network failed.

The official block RPC returns a block `author`, header `height`, `epoch_id`, `approvals`, `chunk_endorsements`, `chunk_mask`, and chunk records with `author`, `shard_id`, and other header fields. [3] Thus a block author or chunk author can be checked against the validator snapshot. A missing block by one expected producer is a validator miss; a chain-level failure requires evidence such as failure of finalized height progression or inconsistent reads from independent sources, not merely one validator's low production.

NEAR's economics specification documents the protocol's performance concepts: validator selection removes validators below `BLOCK_PRODUCER_KICKOUT_THRESHOLD = 0.8` or `CHUNK_PRODUCER_KICKOUT_THRESHOLD = 0.8`; `CHUNK_VALIDATOR_KICKOUT_THRESHOLD = 0.7` is also listed. It describes epoch fields `num_blocks_produced`, `num_blocks_expected`, `num_chunks_produced`, `num_chunks_expected`, endorsement counts, and the uptime/reward calculation. [4] Treat these as protocol kickout parameters, not as proof that a temporary live rate below a threshold already caused a kickout. The same source describes invalid-state slashing as a separate mechanism; a missed production event is not automatically slashing.

NEP-509 describes the validator-role distinction and says block production/validation and chunk production are separate responsibilities; it also states that validators are ordered by non-increasing stake for role assignment and discusses a 2/3-by-stake endorsement condition for chunk validity. [5] This supports separating stake concentration from production performance and treating `chunk_endorsements`/endorsement counts as a distinct signal.

## Functional signals and rules

1. **Stake concentration (current and next set).** Endpoint: `validators` with the current `epoch_id`; fields `current_validators[].stake` and `next_validators[].stake`. Formula: `share_k = sum(top-k stake) / sum(all stake)`; also `HHI = sum((stake / total_stake)^2)`. Window: every finalized snapshot, retain at least one full epoch for trend. Rule: high-impact concentration alert if `share_3 >= 1/3`, because one-third is the protocol's documented Byzantine-stake safety assumption in NEP-509; medium watch if `share_10 >= 0.50` is a product heuristic, not a protocol limit. Current observed result: no top-3 one-third alert (14.459%); top-10 is 35.905%, so the heuristic watch is not met. Impact is reduced independence/fault tolerance; source confidence is high for the fields and arithmetic, but operator/account clustering is not observable from these fields.

2. **Validator block-production miss.** Endpoint: `validators` for a finalized epoch; fields `num_produced_blocks`, `num_expected_blocks`, `account_id`, `is_slashed`, and `prev_epoch_kickout`. Formula per validator: `block_rate = produced / expected` when expected > 0; miss count = expected - produced. Rule: flag a validator performance alert when `block_rate < 0.80` over a completed epoch, matching the documented block-producer kickout threshold; severity high if the account appears in `prev_epoch_kickout`. Current observed result: 3 aggregate block misses and minimum current rate 99.497%; no current `is_slashed` accounts. Impact is localized production/reward loss unless many producers fail; source confidence is high for protocol threshold and fields. Do not infer network failure from this signal.

3. **Validator chunk-production or endorsement miss.** Endpoint and fields are the same; use `num_produced_chunks / num_expected_chunks` and `num_produced_endorsements / num_expected_endorsements`, plus per-shard fields when available. Rule: flag completed-epoch chunk production below 0.80 and chunk-validator endorsement performance below 0.70 only when expected > 0; escalate when `prev_epoch_kickout.reason` is `NotEnoughChunkEndorsements`. Current observed result: 11 prior kickouts for that reason, including 10 with zero produced endorsements and one with 18,623/43,198; this is a real validator-level alert for those named accounts, not a chain-wide alert. Impact ranges from reduced shard participation to kickout; source confidence is high for the observed result, while the 0% current minimum is not sufficient by itself to infer a failure.

4. **Block-author continuity and validator-set membership.** Endpoint: `block` with `finality: "final"` or a specific height; fields `header.height`, `header.epoch_id`, `author`, `header.prev_hash`; compare `author` with `current_validators[].account_id` for the block's epoch. Window: last N finalized blocks, with N at least 100 and preferably one epoch. Rule: flag an invalid-author anomaly if a finalized block author is not in the validator set for its `epoch_id`, or if finalized heights do not advance monotonically. A single absent/late expected producer is a validator miss; a sustained finalized-height stall is network-level evidence only after a second independent read agrees. Current supplied feeds can run the author/set and height checks from FastNEAR RPC and finalized Neardata samples. Impact of an invalid-author anomaly is high; source confidence is high for the fields, but a single RPC endpoint can itself be unavailable.

5. **Network-level failure versus validator miss.** Use FastNEAR public RPC `status` fields `sync_info.latest_block_height`, `sync_info.latest_block_time`, and `sync_info.syncing`, plus finalized `block`; cross-check the same height/hash with FastNEAR Neardata `GET /v0/last_block/final` or `GET /v0/block/{height}`. Rule: classify network-level concern only if finalized height/hash fails to advance across a defined interval (for example, three consecutive polling intervals) or independent RPC and Neardata reads disagree on finalized height/hash; otherwise classify an isolated author/production gap as validator-level. No fixed duration is protocol-backed, so the three-interval rule is an operational test rule and must be labeled heuristic. Impact is chain-wide only on corroborated stall/disagreement; source confidence is medium because both feeds are public providers and may share upstream infrastructure.

6. **Slashing/challenge evidence.** Available now: `validators.current_validators[].is_slashed`, `prev_epoch_kickout[].reason`, and block `header.challenges_result`/`challenges_root` provide direct RPC evidence of current slashing flags, kickouts, and challenge-result fields. Rule: alert only when `is_slashed == true`, a non-empty challenge result is observed, or a kickout reason is returned; never convert a missed block into a slashing alert. A dependable public RPC-only historical slashing/challenge time series is not established by the supplied feeds; add archival snapshots or a free indexed history source before claiming rates or trends.

## Availability and limitations

The current FastNEAR public RPC and FastNEAR Neardata feeds can run signals 1–5 now, provided snapshots are persisted for windows longer than one request. The supplied account-view feed can read a named staking account but cannot, by itself, attribute pooled stake to beneficial owners or independent operators. CoinGecko price/history and DefiLlama price/TVL are not validator telemetry and should not be used to manufacture validator alerts.

The public `validators` response is epoch-scoped. A single current snapshot cannot establish a concentration trend, validator churn rate, or historical miss rate. `current_validators` stake is validator-account stake, not proof of operator independence; clustering by company, hosting provider, key custodian, or common failure domain needs another dependable public source. RPC `block.author` identifies the producer account but does not reveal why a block was late or missed. `chunk_endorsements` is a compact per-block bitmap/byte structure and should not be reverse-mapped to account IDs without the matching protocol/epoch validator ordering; use the aggregate validator fields for the safer current check.
